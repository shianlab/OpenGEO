# 工具体系与选型原则

实践中的资料维护、页面发布、回答观察与问题修正，会产生不同类型的工作。工具选择应从这些工作出发：需要取得什么资料，处理什么对象，交付什么结果，以及谁来判断结果是否合格。一个界面可以同时提供很多功能，实际能力仍须逐项验证。采购之前把这些关系说清楚，才能避免投入之后只获得一组无法复查的分数。

## 一、按工作链路划分工具能力

一套可持续使用的工具体系，可以分为资料发现、内容获取、事实管理、信息供给、运行记录、结果评审、监测分析和协作维护八类能力。它们可以由一个系统提供，也可以分布在多个系统中。系统数量取决于工作规模与衔接成本，功能数量本身没有评价意义。

| 能力 | 典型输入 | 应当交付的结果 |
|-|-|-|
| 资料发现 | 用户任务、主题、检索条件 | 可定位的原始资料及检索记录 |
| 内容获取 | 网页、文档、媒体地址 | 原始文件、解析结果与访问状态 |
| 事实管理 | 对象、主张、来源、条件 | 有身份和版本的事实记录 |
| 信息供给 | 已审核内容、目标入口 | 页面或数据提交结果与接收状态 |
| 运行记录 | 问题、环境、配置 | 回答、引用、运行状态与时间 |
| 结果评审 | 回答、基线、规则 | 可解释的标签、依据和分歧 |
| 监测分析 | 运行与评审记录 | 有范围说明的指标和变化解释 |
| 协作维护 | 变更、责任、审核意见 | 可追踪的修订、发布与更正 |

同一个“抓取成功”在不同环节可能含义不同。资料获取工具成功下载页面，只证明它取得了响应；监测工具发现回答引用该页面，才提供了另一种观察。将二者合并为“AI 已收录”会让工具报告超出它实际掌握的证据。

## 二、先写输入和输出，再看产品名称

选型要求需要具体到可测试的对象。例如，“支持中文”可以拆成中文页面正文提取、中文型号识别、简繁体别名归并、中文问题运行和中文评价解释。一个工具能够处理中文问题，仍可能把中文表格中的单位拆散。这些能力应分别列出，不能用一个语言标签代替。

输出也要区分摘要、记录与判断。摘要便于快速阅读，记录支持复查，判断形成结论。假设系统提示某品牌“引用率下降”，团队需要知道涉及哪些问题、哪些运行、哪些链接，以及分母是否发生变化。如果只能导出折线截图，就难以判定变化来自内容、采样或产品升级。

输入规模和更新方式同样影响选择。几十篇静态文章可以采用人工检索与表格维护；每天变化的上万条商品信息需要批量校验和增量同步；专业内容还需要明确审核责任。把规模、变化频率和错误后果写入需求，会比笼统要求“全自动”更有帮助。

可以把需求写成验收动作。资料工具的动作是“导入一篇有多个版本的论文，并保留实际读取版本”；采集工具的动作是“运行指定问题，导出完整回答和原始引用”；评审工具的动作是“指出一条条件遗漏，并定位对应资料”。每个动作都有可观察结果，产品演示也就有了共同检查标准。

需求还应标明使用者。编辑需要快速阅读材料，研究人员需要查看配置和原始记录，运营人员需要找到待修正入口。工具是否适用，应结合这些实际操作评价。功能存在于某个高级接口中，却无人能够维护，对当前团队的可用价值可能有限。

## 三、把测量覆盖写进工具合同与验收

监测工具的覆盖包括平台、接口或界面、地区、语言、时间、问题集合和运行频率。覆盖中任何一项变化，都可能改变结果。提供某平台 API 的工具，不能直接据此宣称复现了该平台面向普通用户的聊天体验。账户设置、搜索能力、上下文和产品编排都可能产生差异。

还应检查样本怎样生成。供应商题库、关键词改写、团队自选问题和真实业务问题分别回答不同的观察需求。以供应商题库发现行业机会，可以有价值；评价自己的关键业务任务时，仍要检查题库是否包含资格限制、产品版本、价格条件和不适用场景。覆盖应有明确边界，不能用“覆盖全网”替代。

[NIST AI 风险管理框架的测量指引](https://airc.nist.gov/airmf-resources/playbook/measure/)强调在具体使用情境中评价系统，并关注测试、有效性和可靠性。这里可借鉴的原则是让工具结果接受任务检验；它没有提供 GEO 工具认证，也不能为商业产品的可见性分数背书。

## 四、原始记录决定结果能否复查

原始记录至少应保留运行问题、回答全文、可获得的引用信息、运行时间、环境标识、成功或失败状态。解析规则、别名表与评审规则也应有版本。它们共同解释一条指标如何形成。原始记录可以采用文件或数据库保存，关键是能稳定对应，且导出之后仍能理解。

报告中的结论需要反向追踪。点击一个异常指标，应能找到对应回答；从回答中的主张，应能定位支持材料；从材料，应能确认实际对象、条件和版本。界面美观能够帮助阅读，追踪关系才决定团队能否完成纠错。展示层与证据层都需要验收。

第三方产品未开放内部检索材料时，应准确记录不可见范围。可以评价公开回答、显示引用和供应商说明，无法直接观察的候选来源和排序过程应保持未知。填补缺失信息的猜测不能作为工具输出的事实字段。

## 五、权限和数据边界从试用阶段开始

工具试用经常需要上传材料、接入账号或保存浏览器状态。应先划分公开资料、内部业务资料和敏感资料，再确定允许进入哪些系统。一个公开知识库工具不必接入客户合同；一个回答采集工具也不必获得内容发布权限。每个环节取得完成任务所需的最小权限即可。

权限还涉及团队内部访问。编辑人员可能需要看公开主档和修订意见，未必需要看到全部订单或客户身份。数据导出、共享链接、日志与自动化运行都要检查访问范围。删除界面上的一条记录，也需要确认关联文件、缓存和备份如何处理。

工具处理外部文本时，还应把文本当作资料。网页中的指令性内容不能自动改变审核规则、调用权限或发布目标。关于这些风险的机制，可结合[权限边界与信息可信性](https://larkcommunity.feishu.cn/wiki/YauPweUlgig2OtkOlvicVZUonHg)阅读；选型时需要观察产品的实际隔离与人工确认行为。

## 六、成本包含验证、维护和迁移

采购费用只是总投入的一部分。运行消耗、数据清洗、人工复核、接口维护、异常处理和内容迁移都需要资源。工具能节约采集时间，如果同时产生大量错误标签，也可能增加审核工作。成本应按完成合格任务计算，不能只比较一次请求的价格。

可以用一组代表任务试算：执行多少次运行，形成多少条可用记录，人工需要检查多少异常，最终完成多少问题修正。把失败和返工包含在内，再评估扩大规模后的预算。供应商价格与计费范围变化较快，实际采购以当时官方条款为依据，知识库不固定列出可能过时的费用。

还要评估服务中断时的可替代性。问题样本、事实主档和原始回答应有可用的导出格式。迁移后能否保留历史标识、引用关系和评审版本，需要通过一次小规模迁移验证。只有导出按钮，未必足以完成退出。

总投入可以分成初次建设、正常运行和异常恢复三部分。初次建设包含资料整理、规则配置和人员培训；正常运行包含采集与审核；异常恢复包含接口失效、错误修正和历史重算。分别估计后，团队更容易看到成本来自哪里，也能判断降低哪项投入最有效。

退出试验可以选取十条资料、十次运行和对应评审，将它们导出到独立目录。另一个工具或人工应能恢复标识与关系，找到一条答案的原问题和依据。若导出文件失去关系，迁移费用便需要纳入选择，而非在后续预算中突然出现。

## 七、用代表任务和故障任务一起试用

试用集可以包含正常任务、边界任务与故障任务。正常任务检查主要能力；边界任务检查版本、地区、别名、单位和资格限制；故障任务检查超时、重复提交、文件缺失、权限不足和来源冲突。数量依任务复杂度决定，重点是覆盖实际风险。

假设要选择商品资料工具，正常任务是更新一个在售商品价格；边界任务是同名商品具有两个规格；故障任务是下游入口暂时拒绝提交。验收需要看到正确的商品身份、条件明确的价格和可恢复的失败记录。若失败被系统自动改写为成功，后续报告就失去了可信基础。

验收规则应在试用之前确定。哪些结果必须人工确认，哪些错误直接导致不通过，哪些功能可以延后，应写清楚。测试之后临时调整标准来迎合产品演示，会降低选择质量。人工基线和分歧处理可沿用[回答评审方法](https://larkcommunity.feishu.cn/wiki/QqHmwHXbYiStDikQjcjcnLQlnUe)。

## 八、评分可以辅助比较，关键条件单独判断

多个候选产品可以用能力矩阵比较，但不同性质的指标不宜随意平均。缺少数据导出、无法保存原始回答、权限不符合要求等问题，应先判断是否影响任务成立。界面体验和速度再高，也无法补偿某些必要条件缺失。

通过必要条件后，可以按任务重要性比较效率、维护成本与易用性。权重应由团队实际使用要求形成，并说明依据。所谓“综合权威分”或“全平台能力分”，如果没有明确测量对象、样本和验证方式，不能用于证明产品在所有场景都可靠。

Google 对其 AI 搜索功能说明，已有搜索基础要求仍适用，进入支持链接的网页需要满足索引及摘要展示资格，且符合要求不保证一定展示。由此可知，工具关于特殊标记的营销承诺，需要回到平台的实际要求检查。[Google 官方说明](https://developers.google.com/search/docs/appearance/ai-features)仅适用于其相关搜索功能，其他平台应分别核对。

## 九、工具之间的衔接需要明确记录关系

一个实用的组合通常围绕共同标识连接：任务编号对应问题样本，实体编号对应事实主档，资料编号对应来源版本，运行编号对应回答与评审。工具可以分工，标识和关系应连续。手工复制内容时同样需要保留这些对应，避免每次交接都重新猜测。

衔接验收要检查真实数据流。上游更正一条产品事实，下游是否更新正确页面；新增问题之后，采集工具是否沿用对应样本版本；评审规则改变后，历史分数是否标明新旧口径。接口连通仅完成传输，语义对应还需要字段映射与验证。

团队规模较小时，可以先用文件、表格与明确的目录组织完成这一链路。规模增大、并行编辑和持续更新增加后，再引入数据库、内容管理与自动化。扩展由实际瓶颈推动，避免同时引入大量无人维护的系统。

例如，一个小型团队计划维护三十个软件功能页面，每月检查一批用户问题。初步组合可以包括来源管理、事实表、内容编辑和回答记录，先用人工完成条件评审。若资料更新缓慢、运行量有限，额外引入复杂工作流未必节约资源。这是工作规模假设，需要在实际试用中核对。

当页面增加到多个地区版本，且功能主档每周变化，原先手工复制容易漏改。此时可优先增加字段映射和影响清单；若回答量增加，人工筛选成为瓶颈，再增加规则初筛。每次扩展都对应已经观察到的具体问题，工具体系随工作成熟而形成。

工具之间还需要检查错误传播。解析器把版本条件丢失，索引可能放大错值，监测系统又将错误推荐记录为正向出现。验收应安排一次贯穿全流程的异常样本，观察在哪个环节发现错误、谁负责处理、修正后哪些结果更新。这能检验组合能力，单独测试各产品无法覆盖全部交接问题。

## 十、选型结论应说明适用任务与剩余限制

一份合格的选型结论应说明：工具用于哪些任务、测试了什么、哪些结果可复查、仍有哪些未知、需要怎样维护，以及在什么情况下重新选择。结论针对实际工作，不应无限外推为行业通用排名。

工具体系的第一步通常是资料发现。资料身份、版本和证据关系确定之后，抓取、索引、评审才有可靠的对象。[下一篇](https://larkcommunity.feishu.cn/wiki/IEZLwjtZwiQGORk2MJmcCESMnAb)进一步说明检索与来源管理怎样形成一套可长期沿用的研究工作。
