# 回答采集与可复现运行

回答采集把问题样本送入指定环境，并保存实际输出。可靠采集需要说明运行发生在哪里、采用什么配置、得到什么结果，以及哪些部分无法观察。可复现运行意味着后来的人能够理解并重复相应过程，生成结果本身仍可能随平台、时间和随机性变化。

## 一、先界定观察的是哪种产品环境

网页聊天、移动应用、搜索结果页和开发者 API 是不同环境。同一品牌下的产品可能采用不同模型、工具、界面和上下文组织。采集记录应写明实际入口，不能只记录一个平台名称就合并比较。

API 容易形成批量、结构化记录，适合受控问题运行；用户界面更接近某种实际产品体验，但自动化、登录和展示过程可能带来额外限制。两种方式可以分别用于研究，结果应各自保留，不能直接将 API 输出当作普通用户看到的答案。

如果任务研究连续对话，记录还要包含先前轮次和操作。只保存最后一句问题，会遗漏改变结果的条件。一次新会话与已有上下文的会话可以作为不同运行类型，比较时应明确，不能混合后解释为模型自然波动。

## 二、运行清单固定问题与配置

运行清单可以记录任务编号、问题编号、问题文本、样本版本、平台入口、运行时间和会话标识。配置包括可控制的模型、工具、语言、地区、提示和参数。不可获得的信息标为未知，避免用产品推测填入模型版本。

用户问题的原文与测试改写应分开保存。若新增资格或价格条件，问题含义可能改变，应形成新版本。采集工具不能为了让答案更“好看”而静默润色问题，否则后续指标失去对应的任务范围。

配置最好由一次运行计划固定，再由每次实际记录确认。平台拒绝某参数、工具未启用或会话没有重置，都可能造成计划与执行不一致。实际执行记录优先于预期配置，异常需要显式保存。

记录格式可以围绕四组字段组织。任务字段保存问题与样本版本；环境字段保存入口、工具和会话；执行字段保存尝试编号、时间与状态；内容字段保存原始回答、引用及文件位置。字段之间以运行编号关联，便于后续连接评审与统计。

配置中的默认项也需要确认。某次运行没有明确设置搜索，系统可能沿用账户或工具默认值。计划中写“联网”无法证明实际调用搜索，工具调用记录或界面状态才提供相应证据。无法观察调用时，应准确描述记录范围。

## 三、保留原始输出与处理后结果

原始输出包括完整回答、能够取得的引用结构、工具返回信息、错误状态与必要元数据。处理后结果可以包括纯文本、主张拆分、实体识别和标签。两者分开保存，避免解析程序把格式信息和失败细节覆盖。

显示引用的答案应保留链接与对应位置。复制成纯文本可能丢失引用锚点，截图可能难以搜索，最好结合可取得的结构化结果和必要的界面记录。数据格式应遵循实际入口的规则与使用条款，敏感会话需要限制保存范围。

流式回答也需要检查结束状态。网络中断时，已经接收到的文本可能只是半个答案。系统应区分完整输出、截断输出和失败，不宜看到部分文字就记为成功。后续评价可以针对完整记录，截断情况仍进入运行稳定性统计。

界面采集需要保留模块归属与可见标识。自然正文、来源卡片、商品候选和广告可能共享一页，复制文本后却失去边界。可以为每段保存模块类型、位置、链接及标识依据，再与对应运行连接。无法确认付费属性时标为待分类，保留完整采集记录；不能因为卡片靠近答案，就把其中品牌归为模型推荐。分类关系见[回答呈现与商业展示](https://larkcommunity.feishu.cn/wiki/AG9xwgkb6iVsUekQSsVcegfHn3c)。

## 四、搜索接口的引用字段各自解释

[OpenAI 的网页搜索工具说明](https://developers.openai.com/api/docs/guides/tools-web-search)介绍了输出中的引用注解，包含来源地址、标题和相应位置等信息。采集时可以保存这些实际返回字段，帮助定位回答与来源的对应；字段出现本身不证明引用支持了全部主张。

[Claude 的网页搜索工具文档](https://platform.claude.com/docs/en/agents-and-tools/tool-use/web-search-tool)也说明搜索结果和引用的返回方式。工具应按当前接口结构解析，保留无法识别的原始内容。不同接口的字段不能仅靠名称相似就视为等价，需要检查它们的实际含义。

[Gemini 的 Google Search grounding 文档](https://ai.google.dev/gemini-api/docs/google-search)提供了其搜索辅助回答能力说明。采集方案应确认本次实际使用的能力和可获得信息。接口能力、搜索调用与最终回答引用属于不同观察对象，记录时分别保存。

## 五、运行编排工具减少重复操作

编排工具可以组合问题、提示、候选配置与评价条件，自动执行并保存记录。[Promptfoo 入门文档](https://www.promptfoo.dev/docs/getting-started/)展示了以提供方、提示、测试变量和断言组织测试的方式。它能够支持批量比较，评价有效性仍需要团队设计并验证。

不同候选之间应尽量保持任务和输入一致。若某候选获得更详细问题、更丰富上下文或不同搜索权限，比较就包含这些差异。它可以评价两个完整方案，但不能把全部差异归因于单个模型。

编排需要保留顺序、并发和实际执行时间。平台限流、服务更新和批次中断，可能让部分候选在不同条件下运行。采用交错执行或记录时间分布，有助于检查这些差异；具体方案仍取决于接口限制和评价目标。

工具调用记录与最终来源列表应分别保存。系统可能检索多份资料，只在回答中引用其中一部分；显示引用也可能没有足够位置关系供自动评审。采集层只记录实际字段，后续评审再判断哪些材料支持哪些主张，避免在获取阶段提前填入质量标签。

批量计划可以包含固定观察样本与临时诊断样本。临时样本用于调查新错误，固定样本用于时间比较。工具界面应让两者可识别，避免一次调查加入大量异常问题后，总指标下降却被解释为平台整体退化。

## 六、失败和重试保留为数据

失败可以分为限流、超时、权限、参数、工具失败、输出截断和内容缺失。不同类型需要不同处理，错误提示应随记录保存。不能把全部失败自动生成“未提及品牌”的标签，那会把系统可用性问题混入回答内容评价。

重试形成一次新的执行尝试，应记录与原任务的关系。只有第一次成功答案、全部成功答案还是指定尝试进入内容分析，需要预先说明。失败率另行报告，防止通过不断重试挑选合意答案。

若接口支持请求标识或相应去重机制，可以按其规范使用；否则也应在本地记录执行状态，避免断点恢复重复提交。重复请求可能增加成本并产生多个回答，不能任意保留其中最有利的一条。

## 七、重复运行评价稳定性

同一问题多次运行，可以观察回答是否稳定提及对象、保留条件或出现错误。它提供的是该问题在指定环境下的重复结果，无法自动替代更多独立用户任务。十个问题各运行十次，与一百个不同问题各运行一次具有不同统计含义。

重复次数应根据观察目标、波动程度和成本确定。明显高风险错误可以先保留并诊断，稳定性比较需要足够记录。增加运行之前，先检查问题代表性和评审一致性，避免大规模采集放大同一个样本偏差。

即便固定可控制参数，服务更新、外部搜索和内部编排仍可能改变结果。采集工具应保留这些不可完全控制的条件。研究结论可以针对观察范围描述变化，不能声称所有未来运行都会相同。

## 八、界面采集需要记录实际可见状态

界面采集应按照真实操作保存问题、回答、引用和相关设置。是否启用搜索、是否登录、是否存在个性化或历史上下文，需要在可以确认的范围内记录。看不到某项状态时，应标明未知。

自动化运行需要遵循平台访问与使用要求，不能通过绕过限制获得数据。界面变化还可能导致操作失效，例如输入未提交、答案未完成或引用没有展开。采集工具应检查实际状态，避免将空白页和加载页保存为有效回答。

截图用于复查界面，文本用于检索与评审，两者可以关联。保存之前应检查个人资料、账号信息和无关会话是否进入记录。测试账号与真实业务会话最好分开，减少隐私和上下文混入。

新会话验收可以连续执行两个无关任务，检查第二个任务是否继承第一个任务的条件。对于连续对话，则检查指定前文是否完整保留。两种运行都需要正确的会话边界，自动点击“新对话”之后仍应确认实际状态。

同一界面可能分阶段显示正文、引用和补充卡片。工具需要知道采集目标包括哪些信息，并在完成条件满足后保存。回答正文结束而来源区仍在加载，可能造成引用缺失；只等待来源区，也可能漏掉最终补充。可以用代表任务核对完整记录，再确定等待方式。

## 九、统一记录格式，保留入口差异

统一格式可以包含运行编号、问题、入口、时间、输出、来源、状态与配置。不同入口特有字段另行保存。统一方便后续查询，不能为了字段一致而编造某入口没有提供的数据。

引用可以保存原地址与规范化地址，品牌可以保存原文字面与识别对象。规范化规则应有版本，方便之后重算。若直接覆盖原文字面，后来发现同名误识别时就难以恢复。

问题与运行之间可以是一对多关系，运行与评审之间也可以是一对多关系。人工评审和自动评审分别保存，再记录最终裁定。数据结构保留这些关系，统计时才不会把重试、重复引用或多个标签当成独立回答。

## 十、采集方案中的成本与权限

运行成本不仅包括接口请求，还包括搜索工具、存储、人工复核和故障处理。正式扩大之前，可以用一批代表问题测量实际消耗和可用记录数量。按照价格表预估后，还需要与真实运行账单和失败情况核对。

权限应限于运行与读取。需要采集公开答案的任务，通常不需要修改网站、发布文章或取得客户数据。运行配置中的凭据不能写入公开记录，导出数据也要过滤秘密字段。记录可复现与暴露访问凭据之间没有必然关系。

长期运行还需要停止条件。预算接近上限、故障持续、平台规则改变或样本失效时，应暂停相应任务并通知维护者。系统自动持续请求却无人检查，会产生费用和无法解释的数据。

## 十一、一个采集异常的完整例子

以下为机制说明用假设。某批次计划运行四十个问题，其中三条超时，两条只有部分答案。工具应保存四十个计划任务、全部实际尝试和各自状态，内容分析明确使用哪些完整答案，稳定性报告同时显示失败与截断。

若重试后三条超时全部成功，应保存新尝试与旧尝试的关系。不能删除旧失败再宣布成功率百分之百，也不能把五条异常全部计为“品牌未出现”。判断内容表现和运行可靠性需要各自口径。

若批次中途平台更新了界面，后半批问题搜索开关未生效，应将受影响记录标为配置异常。完成修复后重新执行指定部分，并说明替换规则。保留异常记录能够解释结果变化，也帮助后续维护工具。

同一条失败还可能影响多个指标。前述五条异常应进入计划执行状态，三条成功重试进入内容分析时，记录所采用尝试。工具导出可以同时提供任务汇总表与尝试明细，避免维护者在一个混合表中反复猜测哪些行代表同一任务。

采集验收应设置几个已知结构的测试输出，检查工具是否正确保存多段文本、重复域名、引用位置、空来源和截断标记。平台接口升级后，用这些结构样本确认解析仍正常，再执行真实问题。结构解析正确与答案质量正确分别验证。

对于没有引用的完整回答，应保存真实的空引用状态。对于引用字段读取失败的回答，应保存解析异常。两者在报告中具有不同含义，不能全部显示为零引用，否则会将采集故障误判为平台引用能力不足。

## 十二、可复现性从交接检验

可以让另一名维护者使用已保存的样本、配置和说明，在同一可用环境中执行一小批任务。检查能否找到对应问题、理解入口差异、保存原始记录并识别失败。若只有原作者知道按钮在哪里，运行方案尚不具备稳定交接能力。

复查时不要求所有答案逐字相同。应检查过程是否一致、环境差异是否被记录、结果是否能沿同样规则评价。公开平台内部变化无法全部固定，工具的责任是如实保存并帮助解释。

原始记录形成后，下一步是判断回答是否相关、准确、有据并适用。这个判断需要规则、基线与人工校准。[下一篇](https://larkcommunity.feishu.cn/wiki/JceIw7p07i4OOOk89LachMWdnch)讨论评审工具如何承担其中的工作。
