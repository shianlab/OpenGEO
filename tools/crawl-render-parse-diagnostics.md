# 抓取、渲染、解析与访问诊断

资料进入后续检索和回答之前，需要经过获取与转换。诊断工具的任务是把这些过程拆开观察：服务器返回了什么，浏览器执行之后出现了什么，解析程序留下了什么，以及关键事实是否完整。只看页面外观或请求状态，容易遗漏发生在中间环节的问题。

## 一、区分四种可观察结果

第一种结果是网络响应，包括状态、响应头和返回内容。第二种是浏览器渲染结果，包括脚本执行后的正文、交互状态与请求。第三种是解析结果，包括提取的标题、正文、链接、表格和元数据。第四种是平台侧报告或公开展示，它需要来自目标平台的实际观察。

四种结果可以关联，不能互相替代。返回成功状态的页面可能只有登录提示；浏览器中完整显示的内容，可能在正文提取时丢失表头；本地解析成功的页面，也可能尚未被目标搜索系统发现。诊断记录应标明自己掌握的是哪一种结果。

[Google 的 JavaScript 搜索说明](https://developers.google.com/search/docs/crawling-indexing/javascript/javascript-seo-basics)分别讨论抓取、渲染与索引，并指出不同抓取程序处理 JavaScript 的能力存在差异。这说明诊断需要保留环节差别；用一个本地浏览器成功打开网页，无法覆盖所有信息系统的访问方式。

## 二、HTTP 检查从实际返回内容开始

HTTP 检查工具可以取得状态码、重定向链、响应头、内容类型和响应体。检查地址时，需要记录初始地址与最终地址，确认是否被重定向到首页、错误页或登录页。页面返回 200，也可能在正文中显示“内容不存在”，因此状态判断与内容判断需要结合。

还要检查目标正文是否直接存在于返回内容。若页面只包含加载脚本的框架，需要进一步观察动态请求。图片和文件的地址也应单独检查，避免正文页面可用而附件失效。过期地址、大小写差异和错误参数，都可能导致资料进入错误路径。

请求环境会影响结果。登录状态、语言、地区、请求头和网络条件应按诊断需要记录。不要借用个人登录后的成功结果来证明公共可访问性。涉及受限资料时，应使用已获授权的访问方式，诊断目标是确认边界与故障位置，不能擅自绕过限制。

可以为同一地址保存一份响应检查表：初始状态、重定向次数、最终地址、内容类型、目标标题、关键正文、访问环境与失败原因。表格中的“正文存在”应由实际内容确认，避免以文件大小或 HTML 标签数量替代。诊断入口变化之后，也能用同一组字段比较。

编码与压缩同样可能影响读取。文字出现乱码时，应先检查响应声明与实际解码；文件下载不完整时，应检查传输状态与完整性。某些工具把任何返回内容保存为指定扩展名，实际可能下载了错误页。检查文件头与可打开性，可以避免错误文件进入解析流程。

## 三、浏览器诊断观察动态生成过程

对于依赖脚本的页面，可以使用浏览器开发工具或自动化浏览器查看正文何时生成、调用哪些接口、是否出现脚本错误。应先描述真实用户动作，例如打开页面、切换型号或展开费用说明，再检查每一步产生的内容。

[Playwright 的 Trace Viewer](https://playwright.dev/docs/trace-viewer-intro)能够展示记录的操作、DOM 快照、网络与控制台信息，可用于复查自动化测试中的页面状态。它帮助定位内容何时出现或失败，记录的是所配置浏览器流程，不能直接代表其他平台抓取器的行为。

等待条件需要与任务对应。正文出现、关键字段加载完成和媒体可用，比单纯等待固定秒数更容易解释。持续轮询或后台请求可能使“所有网络请求结束”不适合某些页面。诊断时应同时保留最终内容与等待条件，避免把偶然未加载完成误认为资料永久缺失。

## 四、站点抓取工具用于范围检查

站点抓取适合检查大量页面之间的关系：哪些地址可达，哪些链接失效，哪些页面重定向，哪些页面存在重复或标记冲突。它能发现手工逐页检查容易漏掉的模式，也能形成受影响页面清单。[Screaming Frog SEO Spider 用户指南](https://www.screamingfrog.co.uk/seo-spider/user-guide/)提供了相应抓取与配置说明，使用时应依据实际模式确认取得的是原始内容还是渲染内容。

抓取范围应事先限定。域名、路径、文件类型和重复参数会影响数量，无限日历、筛选组合和站内搜索可能产生大量相似地址。选择代表页面与主要路径先检查，再扩展范围，可以减少无意义请求与异常负载。

站点工具报告中的“发现页面数”表示它在当前入口与配置下发现的范围。未发现的页面可能缺少链接，也可能超出配置、受到访问限制或未被提交。报告需要附带种子地址、规则与排除条件，数量才有可解释性。

## 五、正文提取关注语义完整性

网页解析工具通常尝试去除导航、广告和重复页脚，保留主要内容。[Trafilatura 文档](https://trafilatura.readthedocs.io/en/latest/)介绍了网页正文与元数据提取能力，可作为正文处理工具的例子。清理后仍需核对重要条件，页面边栏、脚注或折叠区域可能包含与决策有关的信息。

评价提取质量时，不能只比较字数。标题层级是否保留，表格列名与数值是否对应，否定词是否缺失，版本和适用地区是否仍在，才更接近语义质量。文本很长却混入其他商品信息，同样会污染事实。

假设参数表中“标准版：不提供离线部署；企业版：支持”，解析结果若只保留“支持离线部署”，就把有条件主张扩成全产品能力。应保存原表格或对应截图，让校验者定位转换错误，再修改解析方式或数据表达。

## 六、PDF 文本与扫描图像分开处理

PDF 的视觉布局可能通过文字的绝对位置形成，文件未必具有完整的段落和表格语义。文本提取之后，阅读顺序、表格列关系、上下标与脚注都需要检查。多栏论文和跨页表格尤其容易发生错位。

[pypdf 的文本提取说明](https://pypdf.readthedocs.io/en/stable/user/extract-text.html)明确区分文本提取与 OCR：它可以读取文件中的文字，不能直接识别图像中的文字。纯扫描件需要另行进行 OCR；带有隐藏 OCR 文字层的文件，也需要检查文字层与可见页面是否一致。

OCR 的验收应围绕高影响字符。型号中的字母与数字、负号、小数点、单位、日期和比较符号发生错误，会改变主张。可以先用工具提取，再对关键字段回看页面图像。已有可靠文字层的文件，也无需为了统一流程全部转成图片重新识别。

## 七、表格、图片和媒体保留必要关系

表格应保留行对象、列属性、单位和共同条件。若表格跨页或带有合并单元格，应明确哪个条件作用于哪些记录。转换到表格文件或数据库后，检查空值代表缺失、沿用上值还是明确不适用，避免程序自行猜测。

图片中的信息需要结合图注和正文。一个曲线图的轴、单位、图例与测试条件共同形成意义，提取单个峰值不足以支持完整判断。视频与音频可以获得转写，但重要演示动作、字幕和画面数据需要另外记录。转写结果可以作为处理材料，不能替代对全部媒体信息的理解。

原始媒体、提取内容和解释说明应相互对应。公开页面的文本说明可以提升可访问性，具体要求可结合[WCAG 2.2](https://www.w3.org/TR/WCAG22/)理解。该规范涉及可访问性，不能据此声称媒体补充文本必然提高某个平台的推荐位置。

以下为转换说明用假设。设备表格第一列为型号，第二列为连续输出，第三列为短时峰值；表下注明峰值只在特定时间内允许。提取程序若将第三列与第二列错位，答案可能把短时峰值写成持续能力。字词全部识别正确，事实关系仍发生错误。

修复需要核对表头、行对象和脚注关联。可以将每一行转成带字段名的记录，并将共同条件复制为明确引用或关联条件。转换完成后，使用“连续输出是多少”和“峰值可以持续多久”两类问题检查，确认两项主张各自取得正确依据。

多模态验收还应区分获取失败与识别失败。图片没有下载，属于获取；图片完整但数值识别错误，属于识别；数值正确但图例对应错误，属于关系理解。分开记录后，可以选择修复网络、OCR 或语义转换，减少无效调整。

## 八、建立有代表性的解析验收集

验收集应包含普通文章、长文、参数表、动态页面、扫描文件和受限页面，并记录预期事实。重点覆盖实际业务中的对象和格式，不必为工具追求无关格式的全能性。每种材料同时检查获取状态和语义保存情况。

假设工业知识库的验收集包含十份设备资料，预期字段有型号、额定功率、运行条件、适用标准和有效日期。可以逐项比较提取值与人工核对值，记录缺失和错配。若只有九份取得成功，应把第十份的失败保留在总体记录中，不能从分母静默删除。

大规模材料可以先进行自动结构检查，再抽查正文和关键字段。高影响材料、异常格式和新解析规则需要增加复核。抽查数量由错误风险与资料差异决定，固定抽取一个百分比无法自动保证质量。

验收结果可以分为身份保持、主张保持、条件保持和位置可追踪四项。身份保持检查内容是否仍属于正确对象；主张保持检查数值和判断；条件保持检查版本、时间与限制；位置可追踪检查能否回到原文件。四项分别记录，能够揭示“文字提取很多但关系错了”的情况。

误差容许范围应按字段制定。正文换行与空格变化通常不影响含义，型号错一个字符可能指向另一设备；近似数值是否可接受，取决于来源精度与用途。不要给全部字段统一设一个文本相似度阈值，再据此判断专业资料合格。

对于频繁变化的页面，验收还应包含同一地址两次更新。确认工具取得新内容、原始版本仍可复查、缓存没有覆盖新事实。页面结构改版后，解析器可能继续返回旧区域，因而更新能力需要独立验证。

## 九、失败状态需要明确且可恢复

失败至少应区分网络超时、服务拒绝、权限不足、格式不支持、解析为空和语义异常。不同失败需要不同处理：超时可能重试，权限不足需要确认访问边界，表格错位需要调整转换方法。系统统一显示“未发现内容”，会使诊断失去方向。

重试应记录次数和结果，限制请求频率，并避免对同一地址不断发起请求。即使后来取得成功，也应保留首次失败，便于分析稳定性。工具升级或规则修改后，可以用固定验收集回归检查，确认修复没有损害原本正确的格式。

处理结果应携带来源标识、获取时间、文件指纹或版本标识、解析器配置与异常记录。这样，当后来发现某个错误值时，能够判断它来自原文件、旧版本还是提取程序。记录关系越完整，修正范围越容易控制。

批量任务应保存每个地址的状态，而非只保存一个总日志。一次批次中出现很多异常，可以按类型与页面模板汇总。例如同一模板都缺少正文，可能涉及脚本或提取规则；不同域名都超时，可能涉及运行环境。模式提供调查方向，具体原因仍需检查。

运行资源也应进入验收。记录请求数量、处理时间、内存或存储需求，以及人工修正量。浏览器渲染比静态读取可能消耗更多资源，OCR 与复杂表格处理也需要额外时间。可以采用按实际格式分流的方案，避免全部资料进入最昂贵的流程。

地址规范化和缓存应保留原始关系。去掉参数之前，需要判断参数是否控制语言、型号或时间；忽略这些参数可能把不同内容合并。缓存可以减少重复请求，更新检查则应能识别资料变化，避免长期只读取旧副本。

## 十、区分本地能力与平台实际状态

本地诊断能证明特定环境下的访问与转换情况。目标平台是否发现、采用或展示资料，需要来自平台报告、服务器日志中可确认的请求，或公开回答观察。即便日志出现某类抓取，也应进一步核对身份和访问范围，不能直接推断所有回答都使用了该资料。

工具报告应把已观察事实与分析假设分开。可以写“该页面正文依赖脚本，当前静态解析未取得价格”，并建议调整；无法仅据此写“所有 AI 都看不到价格”。清楚的边界有助于团队选择后续验证路径。
