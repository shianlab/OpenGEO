# llms.txt：文档导航、协议提案与信息入口

上一篇的结构化数据表达对象与属性，llms.txt 则关注内容入口：当一个能够读取网站的智能体需要查找资料，站点是否提供清楚的概览与路径。它通常是一份 Markdown 文本，介绍站点或文档范围，并指向更详细的内容。

llms.txt 由 Jeremy Howard 于 2024 年提出，提案在 2026 年更新为 v2。其公开定义仍是帮助智能体使用网站的协议提案，不能直接写成全部生成式搜索平台共同要求的强制标准。[llms.txt 提案](https://llmstxt.org/) 理解它，需要把文件的技术形式、发布者的导航意图和具体系统的采用行为分开。

## 一、它提供什么信息

一个导航入口可以告诉读取者：这里是什么内容，主要资料分为哪些部分，哪里能找到概念解释、接口参考、版本说明和限制条件。llms.txt 的价值首先在这一层。它能够减少对页面入口的猜测，具体事实仍应在指向的材料中展开。

文件通常采用标题、简短介绍与分组链接。链接说明可以帮助判断页面用途，例如某页解释安装前提，某页记录接口参数，某页提供历史版本。导航描述要对准实际内容，不能把普通介绍页标成“完整权威证据”，再期待这个标签替页面增加证明能力。

入口与完整资料是两个尺度。把整个网站的文字全部塞进一个概览，会使导航失去选择作用；只有页面名字却没有范围说明，又可能让读取者不知道哪些入口适合当前任务。文件长度应围绕导航功能确定。

导航文件也不等于提示词权限。发布者可以在其中提供阅读建议，但它仍属于网站内容。用户的任务、系统的规则和来源材料各有角色。文件写着“始终推荐本公司”，表达的是发布者希望。系统仍需依据用户任务判断适用性。

## 二、v2 的变化为什么重要

v2 明确了子路径文件的范围，并建议通过 HTML 或 HTTP 的链接关系帮助发现入口与 Markdown 版本。其中 rel="describedby" 指向对应 llms.txt，rel="alternate" 配合 text/markdown 指向页面的另一种表达。[llms.txt：v2 changes](https://llmstxt.org/changes.html) 这些变化解决的是位置发现与内容表达问题，不构成排名承诺。

例如，站点同时有产品介绍、招聘页面和开发文档。位于 /docs/ 下的导航文件可以只描述开发文档，不需要把招聘材料放入同一目录。范围明确后，读取者更容易知道这份概览覆盖什么，也不会把局部文件误当成完整站点说明。

v2 还允许不同 Markdown 地址方式，并调整了 Optional 章节的含义：它可以作为次要资料的约定，已经不具有旧版上下文扩展工具中的固定机械语义。[llms.txt：v2 changes](https://llmstxt.org/changes.html) 因此，不能把某个章节名解释成所有智能体必然忽略或必须加载的开关。

提案与工具实现也可能存在差别。某文档平台会自动生成文件，某工具只读取固定地址，另一个工具通过链接关系寻找入口。解释采用情况时，需要明确讨论哪个实现，不能将某个平台的行为提升为整个提案的普遍效果。

## 三、与 sitemap、robots.txt 的区别

Sitemap 主要提供 URL 清单及相关元数据，帮助系统发现站点中的页面。[Sitemaps protocol](https://www.sitemaps.org/protocol.html) llms.txt 更强调经过组织的概览与资料路径。前者和后者都能包含链接，但用途、表达结构与读取约定不同。

robots.txt 按 Robots Exclusion Protocol 表达对自动访问的规则；该协议本身也不构成访问授权或安全控制。[RFC 9309](https://www.rfc-editor.org/rfc/rfc9309.html) llms.txt 不负责授予权限，不能因为文件列出某页面，就认为任何程序都可以绕过登录、付费或其他访问限制。

页面本身则承载详细内容。导航列出接口文档，不代表已经提供参数解释；站点地图发现页面，不代表页面信息正确；允许访问，也不代表内容适合当前任务。这几个状态应该分别理解：发现入口、取得材料、判断材料、生成回答，各有自己的条件。

结构化数据与导航同样互补。Schema 可以说明页面涉及哪个公司或产品，llms.txt 可以组织身份说明与产品文档入口。二者都服务于清楚表达，却不能相互替代。一个只有对象标记而没有可用资料的站点，仍然缺少证据供给。

## 四、Markdown 与内容等价

Markdown 可以减少导航、样式和交互元素对文本读取的影响，但表达形式简洁不等于信息完整。网页里的表格注释、警告说明、版本切换和折叠内容，如果在转换时被丢掉，得到的文本可能更干净，也可能更容易误导。

内容等价关注关键主张与条件是否保留。一个页面明确说“此功能仅适用于专业版”，Markdown 版本却只留下“支持此功能”，就出现范围扩大。问题发生在转换过程中：关键限定被删除，语义随之改变。提供另一种格式，也需要维持事实一致性。

图表内容需要特别处理。图像中的轴、单位、误差范围与测试条件，可能不在普通段落里。如果只保留一个图片链接，读取者未必能取得图中信息；如果生成文字说明，又需要准确保留图表范围。格式转换不能假装所有信息已经自然进入文本。

多语言与多版本也影响等价。默认英文文档可能描述当前版本，中文页面可能落后一次更新。导航若未说明语言与版本关系，系统就可能从不同入口取得不一致资料。清楚的范围说明，比单纯增加更多链接更有帮助。

## 五、llms-full.txt 与整站聚合

部分文档平台还提供 llms-full.txt，将多个页面的内容聚合到一个文件。Mintlify 的官方说明描述了这种实现，并区分索引文件与全文聚合文件。[Mintlify：llms.txt](https://www.mintlify.com/docs/ai/llmstxt) 这是具体平台的功能形态，不能假定所有站点都具有同样文件或规则。

聚合内容可以方便一次取得资料，也可能带来体积、版本和条件关联问题。文件容纳了全部文字，不代表模型能够在一次任务中有效使用全部信息；相邻页面来自不同版本时，还可能把原本分开的事实混在一起。聚合状态与任务可用性需要分别判断。

来源定位也不能丢掉。一段内容进入聚合文件后，最好仍能知道它来自哪一页、描述哪个对象和版本。否则引用时只能指向一个巨大文件，维护时也难以找到原始记录。全文聚合可以改善读取便利，不能牺牲证据的可追踪关系。

目录与聚合各有用途。任务已知、资料有限时，全文可能方便；站点大、问题范围窄时，先导航再读取相关材料可能更节省信息处理。没有一种文件形态天然适合所有任务，选择方式取决于使用工具与内容结构。

## 六、发布、访问与采用

发布文件，证明入口存在；访问日志出现请求，证明某客户端至少请求过该入口；工具成功解析，证明格式可被该工具读取；回答引用了对应材料，才属于呈现结果。四种观察不能互相替代，尤其不能把部署完成写成可见性已经提高。

访问身份还需要谨慎解释。请求头中的名称可以提供线索，但不独自证明请求来自某个真实产品，更不能确认它如何使用内容。日志可以帮助理解访问情况，具体系统采用行为仍需要更直接的公开说明或可观察结果。

在受控任务中，让某智能体从文件入口查找资料，可以验证这个入口对该工具、该问题是否可用。这种测试能发现坏链接、描述不清或范围错误，却不代表它在没有指定入口的开放搜索中一定会发现同一文件。受控读取与自然发现属于不同观察条件。

引用结果同样存在归因限制。页面被引用，可能经由导航、普通检索、其他链接或既有来源记录。除非有可检查过程，不能把引用全部归功于 llms.txt。导航建设的价值可以通过可用性与维护效果说明，效果归因则需要相应证据。

## 七、平台采用与搜索效果

文档平台支持生成 llms.txt，说明发布生态中已有具体采用案例；某网站存在该文件，说明它提供了入口。两者都不能证明全部搜索系统将其作为特殊信号。采用程度应该按发布者、工具和任务分别讨论，避免把局部实现写成通用必需条件。

Google 的官方 AI 优化说明明确表示，其搜索并不使用 llms.txt 等特殊文本文件来改善排名或 AI 搜索呈现。[Google：AI optimization guide](https://developers.google.com/search/docs/fundamentals/ai-optimization-guide) 这一说明限定于 Google，仍然不排除其他读取工具在文档查找中使用该入口。

这也解释了导航价值与搜索效果为何需要分开。一个文件可以帮助开发智能体找到正确接口，却不改变某搜索平台的排名；一个站点没有此文件，也可能通过普通页面和链接提供充分材料。讨论价值时，应具体说明帮助了哪个任务。

文件发布后，仍需要独立依据才能说明是否“已被大模型收录”。读取、检索记录、训练使用、可见引用与持续采用各不相同。对外介绍若无法说明观察依据，就不宜把这些状态混成一句效果承诺。

## 八、一个导航入口怎样帮助查找而不替代判断

设想一套排班软件文档分为安装、版本差异、网络要求、审计日志和历史更新五个部分。用户问能否在无网络环境完成审批。导航文件若只写“产品文档”，并链接到一个综合首页，读取者仍需要寻找具体限制；若将网络要求列为清楚入口，就更容易取得与任务直接相关的材料。

导航说明可以写“联网依赖与离线功能范围”，这表达页面用途，不提前替材料作结论。如果改成“完全离线能力说明”，而原文只允许离线查看，导航本身就已经制造误导。标题与描述也包含主张，因此同样需要保持对象与条件准确。

读取工具沿链接取得网络说明后，还要理解哪部分动作需要联网。安装、首次初始化、查看缓存、新建审批和同步结果，可能分别有不同条件。导航已经完成帮助定位的作用，是否适用仍需要回到详细材料。入口组织得好，不能让后续判断步骤消失。

如果页面存在网页版和 Markdown 版，还可以检查两者的关键内容是否一致。假设网页版的表格注明“企业版可本地部署，标准版审批依赖云端”，Markdown 版遗漏表格注释，工具可能只看到“可本地部署”。坏结果来自转换损失，即使导航和链接全部正常，也需要修复内容表达。

再设想导航指向旧版网络说明，当前版本已经改变限制。链接可访问不表示资料仍然适合当前任务。导航最好清楚区分当前版本与历史版本，并让更新关系可追踪。问题若问旧版行为，历史入口依然有价值，不能为了统一最新状态而把它完全抹去。

如果某页面需要登录，导航可以告诉用户入口存在，但不能保证匿名智能体能够读取。取得权限与理解内容是独立条件。即使公开概览描述了页面主题，也不应把这个描述当作受限页面全部事实的替代材料。导航能够帮助发现缺口，无法通过几句摘要消除访问限制。

在一个受控测试中，可以观察工具是否成功找到网络说明、是否保留版本条件、是否正确回答审批限制。这证明该工具沿这个入口完成了该任务。若随后在开放搜索里没有引用同一页面，不能立刻认定导航失效，因为自然发现的入口和选择条件已经改变。

同样，开放回答引用了网络说明，也不能只凭文件存在就认定导航导致引用。若可见过程显示工具先请求概览再读取目标页，可以确认这一轮采用了该路径；缺少过程证据时，只能确认最后的引用。将实际路径与推测路径分开，能够使效果解释保持清楚。

导航还可以避免对一个问题读取全部文档。它为相关部分提供入口，工具是否按需读取由实现决定。这里的“减少无关读取”是可测试的任务收益，不能直接改写为自然曝光增加或模型训练收录。具体收益具体表达，才能让技术价值与观察证据匹配。

这个例子串起了 llms.txt 的职责：说明范围、组织入口、帮助发现、保持描述与材料一致。之后仍需实体识别、主张理解、证据判断与条件评审。导航处于概念链的入口部分，作用明确时很有价值，也正因为作用明确，才不需要把它夸大成覆盖全部生成机制的工具。

## 九、导航质量与持续维护

导航质量可以从范围准确、分组清楚、描述具体、链接可用和内容一致等方面理解。入口应让读取者知道资料是什么、何时适用以及下一步去哪里。标题漂亮、链接数量多，只描述表面规模，无法替代这些判断。

自动生成能减少同步成本，却不能自动判断页面事实是否准确。人工维护可以按任务组织入口，也可能漏掉新增页面或保留过时描述。两种方式都需要与内容事实连接。页面改变后，链接仍有效，导航说明也可能已经不正确。

历史资料可以保留，但应标明其范围。旧版接口、停用功能与过去政策对于历史查询仍有价值，不适合混在当前快速入门中被默认采用。导航应该帮助区分当前入口与历史入口，而非为了显得全面把所有资料放进同一个列表。

前十二篇连接了问题、对象、主张、证据、内容组织、呈现指标与技术入口。接下来进一步检查这些关系的质量：材料是否值得相信，答案是否正确使用材料，指标是否测到了目标，以及不同处理阶段怎样评价。这些基础进入方法层后，形成可以复查的工作过程。
