# Schema 与 sameAs：结构化数据与身份关系

前面的实体、属性、来源与关系，主要通过自然语言解释。结构化数据把部分信息按明确字段与关系表达，使程序更容易区分名称、对象类型和属性含义。它帮助表达信息结构，事实是否正确、依据是否充分，仍需要回到内容与材料判断。

在网页语境中，“Schema”经常用来简称 Schema.org 结构化标记。严格来说，数据模式、Schema.org 词汇与 JSON-LD 表达格式属于不同层次：数据模式描述组织规则，词汇规定字段含义，表达格式负责把这些信息写出来。本篇先区分这些层次，再讨论 sameAs 如何表达身份关联。

## 一、数据模式、词汇与表达格式

数据模式描述一组数据应具有哪些结构，例如哪些字段存在、字段允许什么类型，以及它们之间有什么关系。不同系统可以使用不同模式。某个数据库字段叫“名称”，并不自然拥有与另一个网站同名字段完全一致的含义，语义一致还需要共同约定。

Schema.org 提供面向网页信息的类型与属性词汇，例如 Organization、Product、name 和 sameAs。词汇让发布者能够以较明确方式说明一个节点是什么、具有什么属性、与另一个节点有什么关系。它是公开词汇，具体搜索产品支持哪些类型，需要查看对应说明。

JSON-LD 是表达关联数据的一种 JSON 格式。它通过上下文说明词汇含义，并允许使用标识符指认节点。[W3C：JSON-LD 1.1](https://www.w3.org/TR/json-ld11/) Schema.org 词汇可以在 JSON-LD 中使用，二者配合常见，但词汇与格式并非同一事物。

可以类比成词典与句子的关系：词汇说明词的含义，格式安排这些词和关系如何写成可处理的数据。格式正确，只证明表达符合某种结构；词汇用得准确，才有助于语义理解；事实与正文一致，则是另一个需要核对的层次。

## 二、结构化数据描述谁

网页可以同时包含多个对象。公司首页可能介绍运营公司、品牌、网站与产品；产品页可能包含产品组、具体型号和销售条件。结构化数据需要分别描述这些对象，并通过适当关系连接，不能将整页中出现的全部属性塞到同一个节点。

Organization 表达组织，Product 表达产品，WebPage 表达网页。三者在一个页面上相关，却不共享全部属性。组织的成立时间不能随意写成产品发布时间，页面更新时间也不能写成公司成立时间。字段类型选择需要与事实归属一致。

属性范围还要与实体粒度对应。某种材料只属于特定型号，某个价格只对应特定套餐，某项服务只在特定地区可用。如果结构化记录将它们提升到整个品牌，就会产生范围扩大。数据越整齐，越需要检查是否保留了正文中的版本与条件。

对产品组和变体，Schema.org 提供 ProductGroup 等类型及关系，用于表达具有共同特征但存在差异的产品。[Schema.org：ProductGroup](https://schema.org/ProductGroup) 这类关系比把不同版本全部写成同一产品更有表达力，但具体能力差异仍需要内容说明。

## 三、name、url 与 @id

name 用于表示读者可识别的名称，url 通常提供与对象有关的网页入口，@id 在 JSON-LD 中用于指认节点。三者可能指向相关信息，却承担不同角色。名称可以变化，页面可以迁移，身份标识则需要尽量保持可区分和稳定。

例如，一家虚构公司“晨桥科技”的官网主页展示多个产品。主页地址可以作为公司入口，产品节点则各有明确身份。如果把所有产品的 @id 都写成同一个主页地址，就难以区分它们。使用不同标识的目的，是防止对象关系被名称或页面容器混淆。

同一对象在多个页面被描述时，稳定身份有助于表达这些记录属于同一节点。但发布者声明一致，不能保证每个外部系统都按这一方式合并。标识的含义与使用效果需要区分：前者是表达设计，后者是系统行为。

内部编号也不天然等同于公共身份入口。企业可以用内部编号管理对象，对外数据则需要按照所用格式与发布环境表达。如果一个编号只有内部系统知道其意义，外部读者仍需要明确名称、类型和关系才能理解。身份管理可以借助编号，不能只剩编号。

## 四、sameAs 的准确含义

Schema.org 将 sameAs 用于指向能够明确说明该对象身份的参考页面。[Schema.org：sameAs](https://schema.org/sameAs) 重点是同一对象的身份。它可以连接具有可靠对应关系的官方身份页或权威标识入口，不能因为两个页面主题相近就建立 sameAs。

公司、旗下产品与创始人各有独立身份。合作伙伴、经销商、兼容产品、投资机构与客户同样各有身份。把这些链接全部加入 sameAs，会把业务关系改写成身份等同，导致数据语义失真。

新闻报道也需要看它是否作为对象身份参考，而不能把所有提及对象的文章都自动加入。报道某次发布活动，可能更适合作为事件或主张的来源；一份完整介绍某组织的参考页面，才更接近身份说明。链接质量与链接用途应分别判断。

sameAs 也不等于“这个页面为我背书”。它声明身份对应，不声明来源赞同对象、不传递通用权威，也不证明页面中的全部事实。若目标对象的行为或能力需要证据，仍应回到具体材料，而非用身份关联替代论证。

## 五、一段示意数据如何阅读

下面以保留域名 example.org 上的虚构组织作说明。这段数据表达的是一个组织节点及其网页入口，字段数量刻意较少，便于理解各层角色：

```json
{
  "@context": "https://schema.org",
  "@type": "Organization",
  "@id": "https://example.org/#organization",
  "name": "晨桥科技",
  "url": "https://example.org/"
}
```

@context 指明词汇环境，@type 声明类型，@id 标识节点，name 提供名称，url 提供入口。这个示例没有 sameAs，因为没有给出可确认的外部同一身份页面。为了填满字段而编造身份链接，会损害数据质量。

如果组织运营一个产品，应另建产品节点并使用合适关系表达归属；如果存在两个版本，应根据实际差异决定如何区分。示例只用于解释基本结构，实际字段选择应由事实和页面用途决定。

这段 JSON 能被解析，也不证明虚构组织真实存在。技术解析成功、词汇使用合适、事实真实、平台采用，分别是不同状态。理解这一点，可以避免把验证工具显示通过误读为事实或效果已经得到确认。

## 六、验证包含哪些层次

语法验证检查格式能否被读取，例如括号、引号与数据类型。词汇检查关注类型与属性是否按预期使用。业务检查关注字段是否表达正确对象、版本与条件。事实检查则核对数据与正文、材料及实际状态是否一致。不同工具覆盖的层次不同。

一个字段填了错误价格，JSON 仍然可能完全合法；把公司和产品写成 sameAs，格式也可能被接受。验证通过只说明某种规则下没有发现特定错误，无法代替实体与主张分析。对关键字段应能回到对应事实依据。

平台规则还有自己的范围。某平台支持某类富媒体结果，会说明必要字段、资格与质量要求；它接受的字段集合可能比完整词汇更小。符合一般语义与满足某平台功能条件，也要分别检查。不能从词汇页面存在某字段推导它必然影响某个搜索功能。

正文一致性尤其重要。如果页面公开写着基础版不支持导出，结构化数据却声称支持，就形成冲突。机器可读内容不应成为一套与读者所见事实不同的宣传口径。不同表达形式可以详细程度不同，关键判断与范围需要一致。

## 七、结构化数据与生成式搜索

结构化数据能够提供明确类型与属性，可能被某些系统读取用于理解信息。具体系统怎样使用、是否读取全部字段，以及对生成回答产生什么影响，需要按其公开说明和实际观察判断。不能由技术可用直接推出排名或引用保证。

Google 的官方 AI 优化说明明确指出，生成式搜索不要求专门的 Schema.org 标记；结构化数据仍按其常规搜索用途处理。[Google：AI optimization guide](https://developers.google.com/search/docs/fundamentals/ai-optimization-guide) 这个结论限定于 Google 的公开说明，不能扩大为所有系统永远不使用结构化数据。

结构化数据与证据还具有不同职责。字段可以清楚声明某项能力，但发布者自己的声明仍需相应材料支撑；用户评论、测试记录和条款限制也可能影响判断。把数据结构整理好，是改善表达的一部分，无法替代证据供给。

同样，站点发布标记，监测工具检测到标记，系统引用页面，是三个独立事件。前两项能够证明部署和识别状态，第三项才是呈现结果。需要保持观察边界，避免把实施完成率改称引用改善率。

## 八、关系选错，比字段缺少更难发现

假设一个产品页介绍晨桥科技、晨桥排班、标准版和企业版，同时列出合作经销商。正确表达需要区分运营公司、产品与版本，并将经销商作为独立对象连接。若把这些页面全部放入公司的 sameAs，数据就声明了不恰当的身份关系，而非只是“链接丰富”。

可以逐项判断：公司法定介绍页是否说明同一组织，产品文档是否描述一个产品，公司社交主页是否明确属于同一组织，经销商官网是否属于另一个组织，媒体报道是否只是提供某项事实。只有身份对应明确的入口才适合在相应实体上表达 sameAs；其他链接应按实际用途保存。

产品能力字段也容易出现类似错误。企业版支持私有部署，标准版只提供云端服务。若页面同时介绍两版，结构化数据却只建立一个无条件产品节点并声明“支持私有部署”，就可能将局部能力扩成整个产品默认能力。应保留版本关系，并在正文清楚说明部署条件。

有些事实不适合简单映射。“适合中小企业”包含用户规模、任务与成本判断，很难仅靠一个类型字段完整表达；“导出速度较快”需要比较环境与测量条件。为了结构化率而把复杂判断压成无条件属性，会损害语义。结构化只表达能够准确映射的部分，复杂关系仍可以由正文解释。

网站节点与组织节点也需要区分。一个网站可能由多个组织共同运营，一家组织也可能拥有多个网站。网站名称包含品牌，不证明网站与品牌在身份上相同。页面节点描述的是内容入口，组织节点描述的是现实对象，不宜因共享 URL 就合成一类。

同一页面出现两个节点的同一名称，也未必重复。例如产品和品牌可能同名，名称相同但类型与关系不同。反过来，两个公司名称不同，也可能是同一组织更名前后的表达。结构化数据需要借助身份依据解决这种关系，不能用字符串相同与否替代。

对重复标记，真正问题是记录是否一致。不同插件各自生成组织节点，若标识、名称和关系冲突，外部读取者可能得到不同表达；如果语义一致，重复本身未必意味着事实矛盾。验证应看节点身份与属性，而不只数页面里有几段脚本。

从内容维护角度，字段清单应能回到事实清单。每一项关键属性是谁确认的、属于哪个对象、正文在哪里说明，都应可查。新增一个属性并不困难，保证它长期准确却需要依据与责任关系。结构化数据因此承担内容质量的表达职责，不能替内容质量承担全部责任。

如果品牌更名，只改页面标题、不改组织节点，两个表达会暂时不一致；如果产品能力变更，只更新字段、不改帮助文档，也会产生冲突。修改范围应由变化性质决定。身份变化检查名称与关联，功能变化检查版本与主张，入口变化检查链接与标识，避免机械全量替换。

这些情况说明，字段缺少往往显而易见，错误关系却可能通过语法验证并长期存在。一个干净的验证结果，只说明工具没有发现它所检查的错误。真正的准确性仍取决于对象辨认、关系选择、条件保留和事实核对，都是前文概念链已经建立的工作。

## 九、关系表达与持续维护

结构化信息也会过时。官网迁移、品牌更名、型号停产、套餐改变，可能影响名称、链接、属性或关系。维护时应识别变化属于身份、入口还是事实范围，并检查正文与结构化表达是否同步。

身份链接失效，需要确认是否存在新的同一对象入口；产品关系变化，需要核对运营或归属；能力更新则需要版本与证据支持。对不同变化采取同一种全量替换，容易丢掉历史，也可能把旧对象错误合并到新对象。

完整性需要结合表达目的判断。清楚、准确且有依据的少量字段，比大量推测属性更有价值。对于没有确认的信息，可以暂不声明；对于无法用某字段准确表达的关系，可以在正文中清楚解释，或选择合适词汇。强行映射会产生语义错误。
