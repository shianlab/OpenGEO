# 国内 AI 平台的公开机制与观察边界

前面各篇建立了共同分析框架，平台差异可以据此拆开：谁决定搜索，工具返回什么，是否继续获取正文，如何组织来源与答案。讨论国内平台时，首先要分清面向用户的聊天产品、面向开发者的 API 和采用某个模型构建的第三方应用。

本篇依据平台官方技术资料分析公开能力。接口能力描述限定在对应服务，不将其自动推广到同品牌 App，也不推测未公开的来源权重、商业合作或推荐算法。

## 一、阿里云百炼：联网能力由接口配置进入请求

阿里云 Model Studio 的官方文档给出了不同接口启用联网能力的方式，例如部分调用使用 enable_search，Responses 形式则通过工具配置。文档也说明了返回搜索来源的设置。[百炼联网搜索](https://www.alibabacloud.com/help/en/model-studio/web-search)

这些公开信息说明，模型调用与外部搜索之间存在应用配置层。请求是否启用相应能力、当前模型是否支持、结果是否包含来源，都需要按具体接口判断。仅看到调用了通义模型，不能确认本次进行了搜索。

来源返回开关与实际查询过程也属于不同观察维度。某个响应没有展示来源，不应只凭这一点确认没有使用任何外部信息；反过来，返回了一组来源，也仍需检查答案是否正确使用。应以文档规定的返回字段和实际过程为依据。

对内容研究而言，可以借助这些接口观察同一问题在不同配置下的变化，但所得结果首先属于受测 API 环境。通义聊天端可能有不同调度、界面和用户上下文，迁移结论需要独立测试。

### 从启用能力到完成搜索，还有哪些状态

联网接口可以从请求、执行和输出三个层次理解。请求层声明可用能力，执行层记录是否发起搜索及取得结果，输出层将资料组织成回答和来源标注。三层状态并不天然一一对应：允许使用工具不等于每次都会调用，调用成功不等于结果足以回答，来源返回也不等于每条主张都有依据。

以一个说明性场景为例，应用询问某产品的当前价格，并开启联网。它可能收到正常的模型响应，但实际工具未触发；也可能已搜索，却只返回旧公告；还可能取得当前价格页，但生成时混入旧套餐。调查应逐层检查，不能把所有结果统称为“通义知道或不知道”。这里描述的是工具化应用的分析方式，不声称上述状态必然发生在某个默认配置中。

兼容某种接口协议，也只说明调用格式具有对应关系。两个服务都接受 Chat Completions 请求，不代表支持相同工具、来源字段和默认搜索策略。协议兼容、模型能力与检索基础设施需要分别识别，避免把使用方式相似误认为内部机制相同。

## 二、智谱：搜索结果与模型综合可以分别观察

智谱的联网搜索文档展示了查询、搜索结果返回，以及结合模型使用搜索内容的方式。公开示例中的 search_result 等结构提供了来源信息的观察入口。[智谱联网搜索](https://docs.bigmodel.cn/cn/guide/tools/web-search)

其机制意义在于可以分开问两个问题：工具返回了哪些材料，模型最后采用了哪些陈述。若相关资料已经在结果中出现，而答案仍遗漏它，调查重点就应继续向上下文组织与生成移动，不能仍将所有原因归于搜索发现。

搜索结果的标题和摘要也可能不足以证明详细结论。应用是否继续读取全文、如何选择片段，需要结合实际实现。文档给出的调用示例描述一种接入方式，并不完整公开智谱全部消费端产品的工作过程。

### 搜索结果应怎样读成过程证据

如果工具返回一个标题、URL 和摘要，可以确认该响应提供了这些内容；若需要判断详细参数，仍要看摘要是否包含足够条件。拿到一份搜索结果列表，与实际读取其中每篇全文，提供的证据深度不同。研究时应保存工具原始返回与最终答案，以便比较哪些信息在综合时被保留、扩展或遗漏。

例如，检索结果写“专业版支持本地部署”，回答变成“该产品可免费本地部署”，其中免费是新增主张，版本也被放宽。这个变化可以通过两份文本直接核验，无需知道模型内部所有权重。反过来，若工具结果本身已经把原文版本条件删掉，问题需要继续回到摘要和来源获取。

因此，开放的返回结构能够增加观察窗口，但不会自动完成事实核验。它最大的价值，是让分析者有机会区分资料进入与答案生成，而非仅凭最终文字猜测全部过程。

## 三、火山方舟：把联网搜索作为应用工具理解

火山方舟的官方工具总览区分豆包搜索 Custom 版与联网内容插件，搜索文档进一步说明两类工具的来源配置存在差别。研究时应记录实际使用的工具、配置和返回，避免把同属联网能力的不同服务当成同一条件。[方舟工具总览](https://docs.volcengine.com/docs/ark/tools-overview?lang=zh)、[联网搜索工具说明](https://docs.volcengine.com/docs/ark/web-search?lang=en)

这些公开说明适用于对应应用接口。具体参数、模型支持范围与版本限制，需要按所使用接口确认；工具名称也不能单独证明某次取得了哪种网页、图文或视频内容。

从这种工具化接口能够确认的是，应用可以将联网获取纳入模型工作过程。它不能证明豆包 App 的全部检索来源、过滤方法和推荐权重，也不能证明某个内容平台的所有页面都可访问。

例如，观察到某次答案引用短视频平台相关材料，需要进一步确认取得的是原始视频、文字介绍、转录还是其他页面的转述。相同平台名下，不同信息入口的语义完整性可能不同。

## 四、DeepSeek：工具调用能力与具体搜索服务分开

DeepSeek 的官方工具调用文档描述了模型提出工具调用、应用执行工具并返回结果的交互方式。[DeepSeek Tool Calls](https://api-docs.deepseek.com/guides/tool_calls/)这能够说明模型如何接入外部能力，不能单凭模型名称确认外部搜索由谁提供、使用哪些索引。

第三方应用采用 DeepSeek 模型，同时接入另一家的搜索服务时，候选范围主要由该应用的工具和配置决定。用户看到同样的模型标签，在不同入口获得不同引用，是机制上可以解释的现象。

对其他模型也应采用相同区分：模型能够调用工具，产品开放某种工具，本次请求实际调用工具，分别需要不同证据。不能把其中一项替代其余两项。

### 模型托管、工具托管与应用编排

同一个模型可以被不同服务托管，再由不同应用接入网页搜索、企业文档或数据库。这里至少包含三项选择：模型由谁提供，外部信息从哪里来，应用怎样安排调用。模型名称相同而答案不同，未必构成矛盾；差异可能发生在工具、来源范围和上下文构建。

在一个常见的应用设计中，模型提出结构化工具请求，应用校验并执行，将结果回传，模型再形成答案。若搜索失败，应用可以重试、更换查询、返回错误或让模型带限制回答。如何处理失败，会直接影响用户看到的是诚实的未知，还是缺乏新证据却依然确定的表述。这一层责任不能全部归给基础模型。

工具名称也不提供内容质量保证。名为“联网搜索”的功能可能返回网页摘要，另一个同名功能可能继续抓取全文；名为“深度研究”的模式可以有更长流程，但具体深度仍应以过程和结果判断。产品标签帮助识别入口，实际信息流才解释它能够完成哪些任务。

## 五、腾讯 TokenHub：搜索调用与引用位置的公开结构

腾讯云 TokenHub 的联网搜索文档给出了启用搜索的请求配置，并说明来源结果、引用标记和搜索调用量的返回位置。文档也提供用户位置这一类查询条件。[TokenHub 联网搜索](https://cloud.tencent.com/document/product/1823/132358)这为区分搜索执行、来源呈现和位置条件提供了公开接口依据，适用范围是对应云服务。

调用量描述发生了多少次搜索，引用结果描述哪些来源以相应格式返回；两者不能直接换算为独立证据数量。一次搜索可以取得多项结果，多次搜索也可能反复遇到同一来源。若回答有几个引用标记，还需要核对它们分别支持哪些主张，不能只按标记数判断答案质量。

位置条件尤其影响本地服务、天气和地区可用性等任务。用户问“附近有哪些选择”时，任务本身就需要位置；用户问一个全球技术定义时，位置未必同样重要。观察不同地区的答案差异，需要保留实际输入条件。不能由这份接口文档直接推出元宝等消费端产品在每次请求中采用相同配置。

## 六、国内内容生态需要按资源形态比较

公开网站、公众号文章、社区帖子、短视频、文档平台和小程序页面，包含不同访问入口与内容结构。一个服务能够引用某平台相关资料，可能取得原文、摘要、转录、截图说明或其他网站转述。资源形态会影响事实完整性，平台名称本身不足以说明读取深度。

例如，视频口播介绍一项功能，画面字幕限定某个版本，评论区又补充后续变化。如果只取得语音转录，版本和后续更正都可能缺失；如果检索到一篇二手总结，来源关系又增加一层。需要确认使用的是哪一种表示，才能评价引用是否足够支持技术结论。

不同内容入口的更新速度也可能不同。官网先改，社区旧帖仍被广泛转述；新视频已经发布，但文字摘要还没有同步。回答中的冲突可能来自信息生态自身的异步更新。应回到对象、版本与来源时间解释，避免把全部现象归为某个模型的固有偏好。

## 七、怎样比较国内平台才有解释力

有效比较应固定用户任务，并记录入口、模式、地区、时间、会话条件和可见工具过程。先比较是否取得相同的关键事实，再比较答案如何处理条件、引用和推荐。不同平台返回的来源数量，不能直接作为质量排名。

如果平台甲引用官网，平台乙引用社区，需要查看两者支持的具体主张。甲可能掌握准确规格但缺少使用限制，乙可能呈现个别经验但不能说明普遍情况。来源类别本身无法决定胜负。

国内内容生态还存在公开网页与登录内内容的差异。[可访问性](https://larkcommunity.feishu.cn/wiki/EUjmwxHW8iJLxNkgDuIc6Qh7njd)已经说明，平台级“能读或不能读”的永久名单不够准确。机制分析应以具体页面与接口为单位，并保留时间边界。

### 云接口、消费端与第三方入口的比较表

| 观察层级 | 能够直接观察的对象 | 解释结果时的重点 |
|-|-|-|
| 云端模型与工具接口 | 请求配置、响应内容、可见工具事件 | 本次启用了什么，实际返回了什么 |
| 官方聊天产品 | 模式、会话、答案与界面引用 | 默认体验及产品自身的调度和呈现 |
| 第三方应用 | 应用所开放的功能和结果 | 模型、搜索服务与应用规则的组合 |
| 单独搜索服务 | 候选网页及检索返回 | 来源范围与排序，尚未包含最终生成 |

这张表说明了比较的单位。百炼、智谱、方舟和 TokenHub 的开发文档，可以帮助理解对应接口，但不能直接替代千问、智谱清言、豆包或元宝的消费端实测。DeepSeek 的工具调用文档则说明了应用接入外部能力的交互，不独立公开所有第三方应用的搜索来源。

如果某篇研究混用这些层级，例如拿一个默认不联网的模型调用，与一个多轮搜索产品比较最新资讯能力，结论会同时包含工具差异和模型差异。它可以描述这两种实际配置的整体结果，却不能据此给基础模型的知识更新能力作出单因素判断。

平台能力研究还应记录响应失败。服务不可用、工具调用未执行、结果为空和返回资料不支持结论，分别需要不同解释。只保留成功样本，会高估稳定性；把所有失败一律记为事实错误，又会掩盖服务状态和任务覆盖问题。

### 一个地区兼容性问题的比较过程

假设要比较不同入口能否回答某设备的地区兼容性，可以固定用户需求、型号、地区和提问方式，记录各入口的模式、时间、会话状态与可见来源。再分别检查候选事实是否正确、适用条件是否完整，以及是否存在无依据的推荐。若某平台允许提供 URL，另一个只进行开放搜索，两组结果应分开，因为发现难度已经改变。

一个入口没有返回引用时，可以评价答案事实，却较难还原依据；另一个返回工具过程时，可以进一步核对搜索和生成之间的变化。不同可观察程度不等于不同实际质量，但会影响研究能够确认到哪一步。比较报告应保留这种证据不对称。

本篇覆盖的公开机制包括模型调用中的联网配置、搜索结果结构、应用执行工具和来源呈现。它们共同说明，国内平台同样需要沿信息流理解。关于未公开索引范围、私有合作数据或推荐权重，应保留未知；这些空白不能用品牌印象或单次答案补齐。

## 八、公开资料不足时怎样表达

官方资料未公开某项内部机制，就应明确标为未公开。用户界面中的搜索过程和引用能够补充观察，却不能凭一次结果推导稳定规则。对 Kimi、元宝及百度等其他入口，也需要分别识别聊天模式、搜索工具和开发接口的范围。品牌之间的比较，只有落实到同类入口和相同任务，才具有可解释性。

公开接口提供了能够复核的机制入口，消费端界面提供了实际使用中的观察窗口。两类证据可以相互补充，但应保留各自适用范围：接口文档说明能力与约束，产品观测说明具体条件下发生了什么。
