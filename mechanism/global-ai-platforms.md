# 国际 AI 平台的公开机制与差异

与[国内平台](https://larkcommunity.feishu.cn/wiki/LXO7wn5hPiqGUdkBC7JcjEmanjz)相同，国际平台也需要区分聊天入口、开发接口和搜索基础设施。品牌名称能够标记产品生态，无法替代具体的请求配置与信息路径。本篇按公开资料比较搜索、网页获取、来源标注和工具调度，不给未公开的排名机制赋予确定权重。

## 一、ChatGPT 与 OpenAI API：产品搜索和工具接口

ChatGPT 的帮助文档说明了搜索功能及来源展示。OpenAI API 的 web search 文档则提供工具调用与来源标注结构，包括 URL 引用信息。[ChatGPT 搜索说明](https://help.openai.com/en/articles/9237897-searching-the-web-with-chatgpt)、[API Web Search](https://developers.openai.com/api/docs/guides/tools-web-search)

两类资料的层级不同：前者描述用户产品，后者描述开发接口。API 能返回某种过程信息，不意味着聊天界面必须展示同样细节；聊天产品的某项行为，也不能自动视为所有 API 请求的默认行为。

内容接入还需要区分搜索与训练。OpenAI 的机器人说明分别列出 OAI-SearchBot 和 GPTBot 的用途及独立控制方式。[机器人说明](https://developers.openai.com/api/docs/bots)允许搜索抓取，不能直接证明内容已经用于训练；禁止训练用途也不能仅凭名称推断所有用户触发访问都会被同样处理。

### 已取得的来源与实际显示的引用

OpenAI 的网页搜索文档区分 sources 与正文引用：前者用于查看相应搜索过程所咨询的 URL，后者呈现与回答关联的引用。[来源字段说明](https://developers.openai.com/api/docs/guides/tools-web-search)这提供了一项具体的机制区分：工具接触的材料集合，可以大于最终展示的引用集合。

因此，一个来源出现在过程列表却没有成为正文引用，不必然意味着访问失败；它可能没有提供最终所需信息，或者其内容被其他来源覆盖。反过来，正文引用也不自动说明该来源在检索中排第一。要分析采用过程，需要对照来源内容与回答主张，不能只比较 URL 是否出现。

引用标注还需要由应用正确呈现。开发接口提供位置和来源信息，前端若在改写、截断或重新排版时丢失对应关系，用户看到的引用可能偏离原始响应。模型输出、API 返回与界面显示属于连续的处理层，研究某个客户端时应确认观察的是哪一层。

## 二、Google Search 与 Gemini API：搜索产品和依据工具

Google Search 的 AI 功能说明提出可能使用 query fan-out，从子主题和数据来源发起多个相关搜索。这解释了答案来源与单次传统搜索结果之间可能存在差别。[Google AI 搜索说明](https://developers.google.com/search/docs/appearance/ai-features)

Gemini API 的 Grounding with Google Search 描述了通过搜索为回答提供依据及返回相关信息的能力；URL Context 则针对给定网址获取内容。[Search Grounding](https://ai.google.dev/gemini-api/docs/google-search)、[URL Context](https://ai.google.dev/gemini-api/docs/url-context)前者承担发现，后者明确了入口，二者可在应用中配合。

Grounding 表示回答与外部资料建立联系，无法自动保证资料真实或推断正确。API 返回的来源信息应继续按照[引用验证](https://larkcommunity.feishu.cn/wiki/AW1gw1T87ioJsIk5kj0cZ07On1e)检查。Google 搜索产品、Gemini 聊天界面和 Gemini API 之间也不能直接互换实验结论。

### 查询扩展和指定网址服务不同任务

从一个宽泛问题出发，搜索可以发起多个相关查询，扩大子主题覆盖；从明确 URL 出发，获取工具则围绕既定入口处理内容。用户提供官网链接后回答更准确，可能只是减少了发现与筛选的不确定性，不能直接证明自然搜索也会优先取得该官网。

将两个工具组合起来，可以先发现候选，再读取更完整材料，但仍需要核对工具的实际状态。搜索结果可能包含标题和片段，URL 获取可能遇到格式、登录或页面处理限制。接口支持两类能力，并不保证每个请求都完成“搜索全部结果再逐篇全文阅读”的流程。

Google 搜索产品的 AI 展示与 Gemini 开发接口也有不同目标。前者处于搜索产品的结果组织中，后者由开发者将工具放入应用。相同的 Google 信息基础设施标签，不能消除任务配置、界面和过程可见性的差异。平台比较应记录具体入口，避免用其中一个代表整个生态。

## 三、Claude：搜索与网页获取分开提供

Claude 平台分别提供 web search 与 web fetch 工具说明。搜索工具用于发现相关网页内容并返回来源，获取工具则处理给定页面或文档。[Web Search](https://platform.claude.com/docs/en/agents-and-tools/tool-use/web-search-tool)、[Web Fetch](https://platform.claude.com/docs/en/agents-and-tools/tool-use/web-fetch-tool)

这种拆分提供了清楚的观察方式：系统是否搜索过，是否进一步取得某个 URL，返回材料是否足够支持答案。找到来源标题与读取全文之间仍有差距，不能因为来源在列表中出现，就默认模型处理了完整文档。

当前官方搜索文档还描述了部分工具版本的动态过滤能力，即在内容进入上下文前筛选结果。它说明候选返回到最终输入之间可以存在进一步处理，但具体支持范围依赖工具与模型版本。不能用旧版本的一次测试，长期代表全部 Claude 产品行为。

### 动态过滤增加了一个可区分的处理层

在支持动态过滤的工具配置中，搜索结果在进入最终上下文前可以再次筛选。由此需要区分原始搜索返回、筛选后材料和最终引用。这个公开能力与前文的候选筛选问题相连：外部资料被搜索服务找到，仍可能因后续处理没有进入生成输入。

过滤可以减少无关内容和 token 消耗，也可能遗漏有用条件，实际收益需要根据任务检查。若一次回答缺少某项限制，仅凭存在过滤能力不能确认限制在这里被删除；还需要相应过程证据。公开架构帮助提出更具体的解释，不等于每次失败都已有确定原因。

工具版本和托管环境也会影响支持范围。同名工具的不同版本可能增加处理方式，第三方托管服务未必同时提供全部能力。文章或实验若只写“使用 Claude”，缺少工具版本和入口，就难以复现。比较应把模型、工具与部署入口作为相关但不同的变量。

## 四、Perplexity：搜索、生成与代理接口需要按版本理解

Perplexity 的官方迁移说明区分 Sonar Chat Completions 与 Agent API；前者继续提供支持，后者包含搜索、URL 获取等工具及按步骤组织的输出。[官方迁移说明](https://docs.perplexity.ai/docs/agent-api/migrate-from-sonar/overview)

这说明讨论平台机制时，必须记录接口与版本。沿用过去的参数名称或输出结构，可能已经无法准确描述当前服务。迁移说明确认的是开发接口层面的能力，不代表消费端所有模式均具有相同工作过程。

搜索服务返回候选与生成服务综合答案，仍应分别评价。即使它们来自同一家平台，也需要检查工具拿到了什么、生成保留了什么，以及最终引用支持了什么。集成程度提高，不会取消这些逻辑区别。

### 工具步骤与最终文本的区别

按步骤返回搜索、获取和文本结果，有助于区分系统做过什么与最后说了什么。一次搜索事件说明请求进入相应工具，一项结果说明工具返回了某种材料，最终文本则说明生成采用了哪些表达。这些过程信息越完整，越有机会定位遗漏或推断的发生位置。

但过程可见性仍有边界。返回一个搜索步骤不必然公开内部索引和排序算法；列出网页 URL 也不必然提供完整读取文本。分析者需要按接口真正暴露的信息判断，不将事件名称扩展成未公开实现。

对于使用不同模型和工具配置的代理接口，研究还应记录具体组合。把某个应用上的优劣全部归给 Perplexity 品牌，会隐藏模型、任务说明和来源范围的作用。平台集成提供便利，评价时仍需要拆开其中影响答案的条件。

## 五、平台差异应落实到可比较维度

| 维度 | 需要核对的内容 | 不能直接推出的结论 |
|-|-|-|
| 搜索触发 | 模式、工具配置及实际调用 | 开启能力意味着每次都搜索 |
| 信息范围 | 返回来源、过滤条件和授权范围 | 可用来源等于全部互联网 |
| 正文获取 | 是否继续获取、解析了哪些内容 | 标题出现意味着全文已读 |
| 上下文处理 | 片段选取、摘要与可见过滤过程 | 搜索排名等于生成采用顺序 |
| 引用与推荐 | 支持关系、推荐语境和必要条件 | 引用数量等于权威或购买意愿 |
| 时间与版本 | 工具、产品、索引及会话状态 | 一次观测代表长期行为 |

比较中还应保持问题条件一致。模型相同但工具不同，是应用配置差异；查询相同但来源不同，是信息范围及检索差异；资料相同而答案不同，才更接近生成处理差异。真实产品可能同时变化多个因素，需要避免过度归因。

## 六、为什么相同问题仍难以直接横向比较

相同文字并不必然构成相同任务环境。一个入口可能保留了用户历史偏好，另一个入口采用全新会话；一个入口已经获取网页全文，另一个只取得摘要；一个模式允许多轮搜索，另一个受到更紧的响应时间限制。最终答案的差异可能同时来自这些环节。

因此，平台比较需要说明比较的是产品整体体验，还是某个机制的表现。前者可以保留各产品默认设置，结论限定于该入口的使用结果；后者则需要尽量固定材料、任务和评价标准，记录无法控制的变量。默认体验较好，不能直接证明底层模型在全部条件下更强；同一组固定材料上的生成表现，也不能完整代表产品的网页发现能力。

当来源和过程不可见时，仍可评价答案的事实准确性、条件完整性与引用支持，但内部原因可能无法确定。将可观察质量和机制解释分开，才能避免把一次答案的差异写成长期、普遍的平台规律。

## 七、四类平台放在同一任务下如何理解

以“比较两款设备在当前固件下的离线能力”为说明性任务。搜索产品需要发现最新固件资料，指定网址工具需要准确获取给定说明，生成模型需要区分离线查看与离线编辑，引用界面需要将结论连接到相关段落。任何一层缺失，都可能使答案看起来完整却不适用。

若某入口只用搜索摘要，另一入口进一步取得全文，后者可能更容易保留细节，但这属于本次获取深度的差异；若两者读取相同资料却给出不同功能结论，更值得检查上下文和生成；若结论相同、来源展示不同，则主要体现引用与界面差异。对照这些状态，比笼统宣布哪个平台“更懂品牌”更有解释力。

如果用户给其中一个入口附上最新说明，另一个入口只收到裸问题，结果不能直接用于评价自然发现能力。材料、问题与工具配置必须一起记录。现实产品整体体验可以照默认使用方式比较，但应把结论限定在该实验条件下，避免偷换为基础模型或搜索引擎的全面排名。

### 产品体验比较与机制实验应使用不同结论

若目标是判断普通用户在哪个入口更容易完成任务，可以采用各产品默认设置，记录完成质量、等待时间和使用负担。这样的比较具有实际价值，结论应写成对应产品配置下的体验差异。它不要求拆掉产品集成优势，但也不能把集成差异全部归给基础模型。

若目标是研究生成阶段怎样使用证据，则可以向不同模型提供同一组已经核验的材料，固定问题与评价标准。此时排除了部分发现差异，却也不再完整代表产品的自然搜索体验。两类实验回答不同问题，使用同一个“哪个更好”的标题容易让读者误读。

时间和成本预算也要匹配。允许某个入口搜索十轮、另一个只搜索一次，得到更完整答案可能反映更高的资源投入。若要比较效率，应同时报告相应资源条件；若要比较最高可达质量，也应说明各自允许了怎样的流程。没有统一预算时，质量差异仍可观察，原因解释需要保留限制。

最后，问题集合决定结论范围。英文公开技术资料、本地中文服务、登录内文件和实时库存，面临不同来源条件。某入口在其中一类表现较好，不能自然推广至其余类别。分类报告有助于保留这些差异，也让读者知道研究结果是否覆盖自己的使用场景。

## 八、平台机制会变，哪些分析单位可以保留

模型型号、接口名称与工具能力持续调整，固定的品牌口诀容易过期；信息进入、筛选、解释和呈现这些功能区分仍然有用。每次更新只需重新核对对应环节：工具是否改变，返回内容是否改变，默认模式是否改变，引用结构是否改变。这样能够保留可比较的记录，又允许具体实现变化。

公开文档确认的是产品声明的能力和限制，实际响应确认的是特定请求发生的事情，两者相互补充。文档支持某功能而一次调用失败，需要调查条件；一次观察到某行为而文档未解释，暂时只能记录现象。把这两类证据分开，可以避免将推测写成稳定机制。

国际平台之间的差异最终要落实到可得信息、处理方式和输出质量。对于没有公开的排序权重或专有来源，保持未知比填入一个漂亮但无法核验的公式更准确。对于已经公开的工具与来源结构，则可以沿具体字段和内容关系继续深入，形成可以复核的机制说明。
